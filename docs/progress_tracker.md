# The Plan

Enrich the plan when new information or decision is made. Also keep track of what has been done already.

Approach: walking steps. Each milestone must be independently demonstrable on real hardware before moving to the next; no milestone depends on unfinished work from a later one.

## 1. Build existing RAD image

Create a build script using make utility. Discover how to test the image most easily. To copy the image on sd card always and physically move the card to RPI is not much practical. Is debugging connection available and how?

**Status: done.** [tools/build.sh](../tools/build.sh) fetches Circle (pinned
`Step44.3`), overlays gpu64's config onto it, and builds
`Source/Firmware` into a `kernel8.img`; `SDCARD=<mountpoint> tools/build.sh`
also deploys it. Verified end-to-end in this environment: clean build from
nothing, and sub-second incremental rebuilds. The vendored source needed
several real fixes to compile against a standards-strict toolchain (mismatched
prototypes, pointer/int comparisons, a missing object in the Makefile, two
missing Circle lib dependencies, an IECBuddy printer driver that isn't
present in this repo or upstream and is now feature-gated) -- see
[docs/hw_testing.md](hw_testing.md) for the full list and the reasoning.

Debugging connection: no, not while the RAD is seated in a live C64 --
GPIO14/15, the only UART pins on the header, are physically wired into the
cartridge's own bus latches (see [gpio_defs.h](../Source/Firmware/gpio_defs.h)).
[docs/hw_testing.md](hw_testing.md) lays out the two testing tiers that
follow from that: a bare-RPi-on-the-bench tier that *can* use Circle's serial
bootloader for a full no-SD-card edit/flash/log loop, and an on-cartridge
tier that instead relies on a microSD extension cable (so the card never has
to physically move) plus an on-screen debug log (`tee_device.h`'s
`CHDMIConsole`, drawn beside the reserved gpu64-output box -- see milestone
2) as the console, since plain `CScreenDevice`/`CSerialDevice` logging turns
out not to work once RAD disables IRQs (see hw_testing.md).

## 2. Display basic pattern

RAD is displaying logger output to the HDMI output when C64 runs. The first step is to display a basic pattern on the screen. This will prove that the RPI is able to control the HDMI output and that the C64 can communicate with the RPI. The pattern should use the 320x200 resolution and 256 colors. The pattern should be generated by the RPI and not by the C64. The C64 should only trigger the pattern display. To trigger it, we will need a simple prg program that will write to the API address space. The pattern can be a simple color gradient or a checkerboard pattern.

**Status: checkerboard test pattern confirmed on real hardware** (RAD
cartridge + RPi 3A+, live C64), via `CRAD::showTestPattern()` drawing
directly into `m_Screen`'s already-negotiated framebuffer, confined to a
reserved top-left box (`GPU_OUTPUT_BOX_W` x `GPU_OUTPUT_BOX_H`, see
`tee_device.h`) that leaves room for the on-screen debug log beside it and
for the eventual real C64-video-passthrough image. Getting here required
fixing two hardware bring-up bugs first -- see "Two hardware bring-up
gotchas" in [docs/hw_testing.md](hw_testing.md): a `KERNEL_MAX_SIZE` too
small for RAD's real `.bss` (total silent hang, zero diagnostic output) and
a missing `armstub=rad-prefetch.bin` in `config.txt` (unstable/garbled
picture, looked exactly like a hardware timing fault but wasn't).

The C64→gpu64 trigger path is now implemented (not yet hardware-verified):
[`Source/TestPRG/gpu64_trigger_pattern.a`](../Source/TestPRG/gpu64_trigger_pattern.a)
is a minimal PRG that does a single `STA $DF0B`. On the firmware side,
`rad_reu.cpp`'s IO2 write handler (inside `reuUsingPolling()`, the same loop
that services REU's own $DF00–$DF0A registers) recognizes writes to $DF0B
and calls `CRAD::showTestPattern()` via a `g_pRAD` global (declared in
`rad_main.h`, set from `CRAD`'s constructor) -- kept as a free-function
indirection (`gpu64_showTestPattern()` in `rad_main.cpp`) so `rad_reu.cpp`
doesn't need to pull in the full Circle/screen include stack. Since the C64
is DMA-halted for the entire REU polling session, drawing synchronously
inside the write handler only delays the already-frozen CPU rather than
risking any bus-timing corruption -- next step is confirming that on real
hardware.

- IO decoding: gpu64 uses the unused remainder of IO2, $DF0B–$DFFF, leaving REU's 11 registers ($DF00–$DF0A) and all of IO1 alone — coexists with REU in all three target setups (RAD-as-REU, C64 Ultimate with RAD's REU switched off, original C64 + expansion port multiplier with a real hardware REU). See [project_description.md](project_description.md#io-address-space-allocation), including the open item to verify the Ultimate's REU doesn't mirror across the full IO2 page.
- Trigger PRG just needs a single STA to a $DF0B+ offset to kick off the pattern; no data payload yet.

## 3. Display sniffed current C64 screen buffer

**Design decided, not yet implemented -- see
[docs/bus_access_design.md](bus_access_design.md) for the full reasoning.**
Continuous cycle-by-cycle bus sniffing (the originally imagined approach)
turned out not to fit this hardware: RAD's board only exposes the full
16-bit address to the RPi through a multiplexed latch that's cheap to read
only while the CPU is already DMA-halted, so catching every write to
arbitrary RAM while the C64 free-runs isn't feasible in software without
either a permanent bus takeover or a PCB change. Both were rejected --
**gpu64 must not intercept the C64 bus completely; the C64 stays in charge
at all times**, and no hardware redesign is being pursued right now.

Revised scope, explicitly *not* aiming for cycle-perfect VIC-II replication
here (that remains milestones 5/7's job, only once the API-driven mode
exists): periodic, brief DMA-held snapshot polling (same technique already
used for menu injection and REU/GeoRAM emulation) reads the current VIC-II
register block, screen RAM, color RAM, and character set, then releases the
bus back to the C64 -- a poll, not a permanent takeover. Good enough for
basic legibility (e.g. a directory listing visible on the HDMI screen),
not for running arbitrary demos. This polling only runs when gpu64's own
320x200 API (milestone 4) is *not* currently in use by a C64 program --
the two modes are mutually exclusive at any moment: once a program engages
the gpu64 command API, snapshot polling stops entirely.

- Scope: standard text mode only (40x25, one character set, border/background/multicolor text-mode nuances deferred to milestone 5).
- Needs VIC bank detection (CIA2 $DD00) and screen/charset pointers (VIC $D018) as part of each snapshot, not just the power-on default addresses -- see bus_access_design.md's open questions for polling rate and DMA-burst sizing.

## 4. Basic 2D GPU API

Design and implement the first version of the C64→gpu64 command protocol over the IO1 register window from milestone 2. Minimum viable set:

- Framebuffer clear / fill
- Set pixel, draw line, draw rect (filled + outline)
- Blit a block of bytes from C64 (RAM or REU-transferred data) into the framebuffer
- Palette control (select 256 colors out of the 16M palette)
- Page flip / vsync signal (front/back buffer swap, so C64-side code can build a frame without tearing)

Design questions to settle here: single-byte command + argument bytes vs. a small opcode+length packet; how bulk pixel data crosses the port efficiently (this is the main bottleneck — expansion port bandwidth, not RPi compute); synchronous (C64 polls status) vs. use of the existing NMI/IRQ line for completion signaling.

## 5. Extend VIC-II sniffing

Broaden bus sniffing beyond milestone 3's default text mode: bitmap mode, multicolor mode, sprites (position, shape, color, priority/collision registers), raster IRQ timing, smooth scrolling (fine-scroll X/Y registers), and VIC bank switching via CIA2. Goal: gpu64 can mirror what real C64 demos/games already do on VIC-II without any code changes on the C64 side, by watching $D000–$D02E and the relevant RAM.

- Reference implementation: port/adapt VIC-II rendering logic from VICE (see [project_description.md](project_description.md)) rather than re-deriving it from the datasheet.

## 6. 3D API layer

Add a 3D scene API on top of the 2D layer from milestone 4, OpenGL-ES-inspired but scoped to what a 6502 bus and an RPi 3A+ can realistically drive:

- Vertex buffers uploaded from C64 (or REU, since gpu64 and REU coexist — vertex/texture data can live in REU and be DMA'd)
- Basic transform pipeline (model/view/projection matrices, computed C64-side or gpu64-side — TBD)
- Triangle rasterization with flat/Gouraud shading, simple texturing
- Depth buffering (screen is only 320x200, so a full z-buffer is cheap on the RPi side)

This is the highest-risk/most-open milestone; expect the scope here to narrow once milestone 4's protocol overhead is measured on real hardware.

## 7. Full native VICII feature parity

Mature milestone 5 into a selectable **VIC-II replication mode**: full native VIC-II behavior (all graphics modes, sprite-sprite/sprite-background collision, raster effects, border tricks), reconstructed purely from bus-sniffing, with no C64-side code changes. This is a separate, mutually exclusive mode from the milestone 2/4/6 **gpu64 framebuffer mode** (see note below) — not a merge of the two. Long-term target, not a hard requirement for the project to be considered a success.

**Note on the two modes:** the 320x200x256-color gpu64 framebuffer (milestones 2, 4, 6) is a pure framebuffer — it has no sprite objects, no sprite-sprite/sprite-background collision detection, and none of the other stateful VIC-II hardware features. Sprites, collisions, etc. only exist in the separate VIC-II replication mode (milestones 3, 5, 7), which sniffs and reconstructs actual VIC-II register/RAM state rather than exposing a new API. A C64 program picks one mode or the other; gpu64 doesn't emulate VIC-II hardware semantics *through* the new API.

## Known issues

- **RAD's menu music (SID digi playback) is silent on real hardware**,
  despite `music.wav` loading and converting correctly (confirmed via the
  on-screen log) and the C64's audio-out being confirmed working with the
  original, non-gpu64 firmware on the same hardware. `detectSID()` now logs
  `SIDType`/`hasSIDKick`/`supportDAC` on-screen, and a likely root cause was
  found by inspection: `SIDType` is never assigned anywhere in this vendored
  firmware, so the Mahoney-technique lookup table always defaults to
  `lookup8580` regardless of the real chip. See the "Open item" at the end
  of [docs/hw_testing.md](hw_testing.md) for the full writeup and next step.
