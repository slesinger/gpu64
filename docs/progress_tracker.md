# The Plan

Enrich the plan when new information or decision is made. Also keep track of what has been done already.

Approach: walking steps. Each milestone must be independently demonstrable on real hardware before moving to the next; no milestone depends on unfinished work from a later one.

## 1. Build existing RAD image

Create a build script using make utility. Discover how to test the image most easily. To copy the image on sd card always and physically move the card to RPI is not much practical. Is debugging connection available and how?

## 2. Display basic pattern

RAD is displaying logger output to the HDMI output when C64 runs. The first step is to display a basic pattern on the screen. This will prove that the RPI is able to control the HDMI output and that the C64 can communicate with the RPI. The pattern should use the 320x200 resolution and 256 colors. The pattern should be generated by the RPI and not by the C64. The C64 should only trigger the pattern display. To trigger it, we will need a simple prg program that will write to the API address space. The pattern can be a simple color gradient or a checkerboard pattern.

- IO decoding: gpu64 uses the unused remainder of IO2, $DF0B–$DFFF, leaving REU's 11 registers ($DF00–$DF0A) and all of IO1 alone — coexists with REU in all three target setups (RAD-as-REU, C64 Ultimate with RAD's REU switched off, original C64 + expansion port multiplier with a real hardware REU). See [project_description.md](project_description.md#io-address-space-allocation), including the open item to verify the Ultimate's REU doesn't mirror across the full IO2 page.
- Trigger PRG just needs a single STA to a $DF0B+ offset to kick off the pattern; no data payload yet.

## 3. Display sniffed current C64 screen buffer

Passively sniff the VIC-II bus during standard text mode (the default screen the C64 boots into) and reconstruct it on the HDMI output: read screen RAM + color RAM + character ROM/charset contents as the C64 writes them, translate PETSCII cells to the 320x200x256-color framebuffer. No C64-side code changes and no new API yet — this proves bus-sniffing itself works before any API is layered on top, and gives a always-available fallback view (e.g. showing the C64's actual screen instead of a static test pattern).

- Scope: standard text mode only (40x25, one character set, border/background/multicolor text-mode nuances deferred to milestone 5).
- Needs read-only bus sniffing of VIC-II-relevant writes (RAM at $0400/$D800 by default, changeable via CIA2 bank register and VIC memory pointers — start with default addresses, handle bank switching later if needed).

## 4. Basic 2D GPU API

Design and implement the first version of the C64→gpu64 command protocol over the IO1 register window from milestone 2. Minimum viable set:

- Framebuffer clear / fill
- Set pixel, draw line, draw rect (filled + outline)
- Blit a block of bytes from C64 (RAM or REU-transferred data) into the framebuffer
- Palette control (select 256 colors out of the 16M palette)
- Page flip / vsync signal (front/back buffer swap, so C64-side code can build a frame without tearing)

Design questions to settle here: single-byte command + argument bytes vs. a small opcode+length packet; how bulk pixel data crosses the port efficiently (this is the main bottleneck — expansion port bandwidth, not RPi compute); synchronous (C64 polls status) vs. use of the existing NMI/IRQ line for completion signaling.

## 5. Extend VIC-II sniffing

Broaden bus sniffing beyond milestone 3's default text mode: bitmap mode, multicolor mode, sprites (position, shape, color, priority/collision registers), raster IRQ timing, smooth scrolling (fine-scroll X/Y registers), and VIC bank switching via CIA2. Goal: gpu64 can mirror what real C64 demos/games already do on VIC-II without any code changes on the C64 side, by watching $D000–$D02E and the relevant RAM.

- Reference implementation: port/adapt VIC-II rendering logic from VICE (see [project_description.md](project_description.md)) rather than re-deriving it from the datasheet.

## 6. 3D API layer

Add a 3D scene API on top of the 2D layer from milestone 4, OpenGL-ES-inspired but scoped to what a 6502 bus and an RPi 3A+ can realistically drive:

- Vertex buffers uploaded from C64 (or REU, since gpu64 and REU coexist — vertex/texture data can live in REU and be DMA'd)
- Basic transform pipeline (model/view/projection matrices, computed C64-side or gpu64-side — TBD)
- Triangle rasterization with flat/Gouraud shading, simple texturing
- Depth buffering (screen is only 320x200, so a full z-buffer is cheap on the RPi side)

This is the highest-risk/most-open milestone; expect the scope here to narrow once milestone 4's protocol overhead is measured on real hardware.

## 7. Full native VICII feature parity

Mature milestone 5 into a selectable **VIC-II replication mode**: full native VIC-II behavior (all graphics modes, sprite-sprite/sprite-background collision, raster effects, border tricks), reconstructed purely from bus-sniffing, with no C64-side code changes. This is a separate, mutually exclusive mode from the milestone 2/4/6 **gpu64 framebuffer mode** (see note below) — not a merge of the two. Long-term target, not a hard requirement for the project to be considered a success.

**Note on the two modes:** the 320x200x256-color gpu64 framebuffer (milestones 2, 4, 6) is a pure framebuffer — it has no sprite objects, no sprite-sprite/sprite-background collision detection, and none of the other stateful VIC-II hardware features. Sprites, collisions, etc. only exist in the separate VIC-II replication mode (milestones 3, 5, 7), which sniffs and reconstructs actual VIC-II register/RAM state rather than exposing a new API. A C64 program picks one mode or the other; gpu64 doesn't emulate VIC-II hardware semantics *through* the new API.
